<div class="abstract" markdown="1">
**摘要。** 大语言模型（LLM）智能体可以执行任务，但还不足以经营一家组织。多智能体框架已经证明，角色、工作流与质量控制可以在单个项目之内模拟出来；然而，对于那种带着持久角色、组织记忆与可机器检验的验收标准的 AI 间协作，至今还没有一种被广泛采纳的约定。本文呈现的，是面向一人公司（one-person company，OPC）操作系统的一项设计研究——所谓一人公司，就是由一位人类创始人统率一支 AI 员工队伍的企业。我们提出四套环环相扣的机制：（i）结构化的工作单（work order）协议，角色之间借此交换义务与证据，而不是自由对话；（ii）四层上下文架构，其中隔离边界即责任边界，会话被当作耗材，知识则作为资产不断积累；（iii）模型分级制度，由 token 经济学把异构模型分派到规划、开发、执行、验证四个席位，并以跨厂商验证来抵御相关幻觉；（iv）为人类留出一个明确的位置——作为流水线上的一个节点，通过 *blocked_on_human* 工作单状态接入流程。我们认为，OPC 不会取代行业，而是释放供给——一些此前对单个人来说过于沉重的业务形态由此变得可行——而且它的组织模式是自相似的：先在三人工作室中验证一次，再复制成各个部门，每复制一次，创始人的角色就上升一级。
</div>

## 引言

基于 LLM 的智能体已经从单用途助手演进为协作系统。该领域的综述记录了智能体画像、智能体间通信与能力增长机制三方面的快速进展<sup>1</sup>。在软件工程领域，ChatDev 证明，扮演社会角色的专门化智能体——分析师、程序员、测试员——可以通过结构化对话走完整个开发生命周期<sup>2</sup>；MetaGPT 则把标准作业程序（SOP）编码进提示（prompt）序列，把多智能体协作当作一条由各角色专属工件（artifact）组成的流水线<sup>3</sup>。这些系统确立了一个重要先例：只要脚手架搭得合适，一群 LLM 智能体就能表现得像一支运转中的团队。

然而，团队不是公司。上述框架都是*项目级*的：它们拆解一个任务、执行完毕、随即解散。公司是另一种东西。它跨项目存续；它拥有不断积累经验的角色、约束信息流动的边界，以及比任何单一任务都活得久的流程——预算、验收、上报。我们在此要回答的问题，不是 AI 能否执行任务——这已有定论——而是 AI 能否经营一家组织——这仍是开放问题。

我们借助制度经济学的一个观察来切入这个问题。科斯（Coase）追问公司为什么存在，答案是公司节约了协调的交易成本<sup>4</sup>。我们把镜头倒转过来看：人类公司*是被人类的约束塑形的*——通信带宽有限、记忆不可靠、失败不透明。AI 员工的约束不同：上下文窗口有限、会满怀自信地幻觉、同一模型家族内部存在相互关联的盲区。因此，为 AI 而设计的公司不应模仿人类公司的组织结构图，而应当针对 AI 真实存在的弱点来做工程。现有框架提供了对话机制<sup>5</sup>，实践者也越来越主张用简单、可组合的模式取代复杂脚手架<sup>6</sup>，但两者都没有提供组织层——那种语义可强制执行的“公司邮件系统”。

本文要提出的正是这样一层：一套用于 AI 间委派的工作单协议、一种分层上下文隔离架构、一套模型分级纪律，以及人类在流程中一个被明确定义的位置。随后我们推导出使 OPC 可行的业务筛选标准，并说明这套模式在不同规模下是自相似的。这是一篇设计立场论文：各项机制都建立在已部署智能体系统上观察到的失败模式之上，但把它们组装成一个完整的“公司”，尚未经过纵向验证——这一点留待“讨论”一节展开。

## 结果

### 智能体间协作的工作单协议

AI 间协作的核心缺口不是智能，而是交换格式——一种让一个角色能把义务、验收标准与证据传递给另一个角色的约定。在 TCP/IP 出现之前，两台机器已经能交谈；它们做不到的是*联网*。工作单之于 AI 员工，正是对应的原语：公司备忘录（memo）的正式化。下面的最小 schema 即定义了这一格式。

```yaml
id: 081
type: build            # build / operate / analyze / improve / govern
parent: "007"          # parent work order — orders form a tree
objective: |
  Add full-text RSS output to the blog.
acceptance:            # MUST be machine-checkable
  - bundle exec jekyll build exits 0
  - /feed.xml contains a <content:encoded> node
  - all five page checks return HTTP 200
inputs:
  - repo:example/site, branch:main
  - order:006 (design decision)
constraints:
  - no new gem dependencies
role: dev
model_tier: std        # decided by the planning role, priced per token
priority: P1
status: open
budget: 500k tokens    # over budget = escalate, don't improvise
```

整个系统由两个字段撑起。**验收标准**必须可被机器检验：一条退出码为零的命令、一段能被 grep 干净的字符串、一项越过阈值的指标。“Looks good to me”（“我看着没问题”）正是人类组织积累技术债的方式；而一家接受这种表态的 AI 公司，无法把回路真正走完——因为 AI 对 AI 的验收最终是*执行*出来的，不是*感觉*出来的。与之配套的字段是**证据**：完工报告必须附上验证输出——测试结果、diff、日志——验收角色据此逐条勾核各项标准。验收与证据合在一起，构成一条让每个决策都可回放的审计轨迹。

同样重要的是工作单刻意排除的东西：对话。角色之间交换的是结论、约束与“完成”的定义，而不是各自的推理过程。这是抵御上下文污染最有效的一招；上下文污染是这样一种失败模式：某个角色半生不熟的想法渗进另一个角色的工作记忆。人类世界里有熟悉的对应物：会议用来探索，备忘录用来定案。

工作单分为五种类型——*build*（构建新资产）、*operate*（维持运行）、*analyze*（把信息转化为判断）、*improve*（修复与迭代）、*govern*（预算、审计与例外处理）。三种触发器把工作单注入系统：创始人的目标（由某个规划角色分解成一棵树）；日程（巡检、报告）；以及事件（CI 失败、市场变动、用户反馈）。

### 分层上下文隔离

如果说工作单是管道，上下文隔离就是平面图。支配性的规则是：

> 隔离边界就是责任边界，也就是可见性边界。一个角色的上下文，应当是完成其工作所需的最小信息集。

这是把最小权限原则用到记忆上。它事关污染，也事关访问控制：财务角色的会话里装着敏感数字，开发角色绝不该随身携带——正如一张实体工牌能打开这扇门、却打不开另一扇。整个架构分为四层（**图 1**）。

<img src="/assets/images/fig1-context-architecture.svg" alt="面向 AI 员工的四层上下文架构" loading="lazy">
<figcaption class="figcaption"><b>图 1 | 四层上下文架构。</b> 身份层与知识层持久保存；每张工作单都在一个全新的会话中运行，只注入第 1、2 层中与任务相关的切片，外加工作单本身；交换层是角色之间唯一的通道。写回回路把已结束会话中的经验教训送回知识层——会话由此成为耗材，知识则成为资产。</figcaption>
</figure>

随之而来的关键原则是：**会话是耗材，知识是资产。**一项工作结束后，会话即被丢弃，但它的经验教训——踩过的坑、发现的模式、修订过的规则——会被写回知识层。AI 员工正是靠这条回路成长，也正是它让隔离变得负担得起：只要值得保留的一切都在离场时被抽取干净，上下文就可以放心地烧掉。这一动机有实证支撑：长上下文模型确实会漏用埋在输入中段的信息<sup>7</sup>，因此一个随身携带不断增长的原始历史的员工，不是在积累智慧，而是在稀释智慧。

隔离带来三重红利。**可审计性：**每个角色的工作都是自成一体的一部卷宗，任何失败都能精确重演——是谁、对什么做出了判断。**可定位性：**错误总能落到某个角色、某一步骤上，而不是一团迷雾。**可替换性：**一个容易幻觉的员工可以被整体换掉——连同身份、知识库等一切——而对公司其余部分零干扰。

### 模型分级与异构验证

AI 员工不应全部跑在同一个模型上，理由与公司不会给每个人都付资深员工的薪酬相同。token 经济学迫使公司进行分级（**表 1**）。

| 级别 | 典型工作 | 模型类别 | 理由 |
|---|---|---|---|
| 规划 | 分解目标、设计方案、验收成果 | 可用的最强模型 | 决策一旦出错代价最高 |
| 开发 | 核心实现 | 强模型 | 这里的质量决定其他所有环节的返工量 |
| 执行 | 运行脚本、日志分析、巡检摘要 | 廉价/本地模型 | 体量最大、可机械校验、失败成本低 |
| 验证 | 验收、测试、交叉评审 | **不同厂商** | 目标是异构，不是更强 |

**表 1. 模型分级。** 角色按决策成本与工作量的高低分配到相应的模型类别；验证级别的硬性要求是跨厂商异构。

验证级别值得着重说明：它的要求是*不同*，而不是*更好*。幻觉是当前 LLM 一个有充分文献记录的性质<sup>8</sup>；而对一家 AI 公司来说，真正相关的失败模式不是孤立错误，而是*相互关联*的错误——由同一模型家族驱动的开发者和评审者共享同一批盲区，会满怀信心地把同一个 bug 漏掉两次。由另一家厂商的模型来执行验收检查，就能把相关错误变成独立错误。因此，按角色分配模型不只是成本优化，更是风险控制。

最后，让成本可见。每张工作单都带着 token 预算；每张完成的工作单都把实际开销入账。公司于是有了真实的财务：每个角色对应一份可度量的薪酬支出，成本超支以异常信号的形式浮出水面、触发上报，而不是无声地浪费。创始人应当像 CEO 读损益表那样读 token 账单——因为它本来就是一张损益表。

### 人是流水线上的节点

关于 AI 公司的流行想象，是把人放在机器之外充当监工。更有用的图景不是这样：人是流水线*上*的一个节点——异构，但属于流程的一部分。有些步骤确实需要一具肉身：签一份文件、收一批货、跑一趟银行、亲自出席一场会议。早先的框架把这视为不合格的判据——“这业务没法自动化，因为第七步是线下的。”这个结论是错的。一个线下步骤不会打断流水线，只是让它暂停（**图 2**）。

<img src="/assets/images/fig2-order-state-machine.svg" alt="带 blocked_on_human 状态的工作单状态机" loading="lazy">
<figcaption class="figcaption"><b>图 2 | 工作单状态机。</b> 工作单按 open → claimed → in_progress → done 流转。线下步骤把工作单暂停在 *blocked_on_human* 状态；人类交回证据后，AI 流程随即恢复。验收失败则把工作单打回返工。</figcaption>
</figure>

这个重构之所以重要，是因为人的时间贵在*认知*，而不是贵在执行。打包一个箱子不会让谁的脑力枯竭；它消耗的只是人的在场。拖垮独立创业者的，很少是那件十分钟的任务——而是上百件十分钟的任务，每一件都要求把项目状态在脑子里重新加载一遍。AI 公司吸收掉认知负荷，只把需要肉身的时刻交还给人。因此，OPC 的价值边界不是“AI 能做什么”，而是人能以多低的成本补上 AI 做不到的部分。

有一种工作单永远不会离开人的手：*govern*。预算、发布与对外承诺都可以由 AI 起草，但一家没有人对自己的承诺负责的公司，没有人愿意跟它做生意。创始人把守着大门——这是全公司最廉价的岗位，也是唯一无法委派出去的岗位。

### 选择回路能闭合的业务

单人项目很少死于执行失败；它们死于断掉的回路：

```
produce → distribute → convert → deliver → repeat
```

技术出身的创始人会在第一阶段过度投入，让其余阶段挨饿：产品在那里，却没人知道、没人付费。挨饿的那些阶段——获取关注、转化、服务、从数据中学习——高度数字化、高度可模板化，恰恰是 AI 员工适合干的活。因此，OPC 的第一个战略决策不是组织结构图，而是业务：选一门回路能闭合的生意。四条标准由上述机制推出：端到端全数字化（每个阶段都在智能体可及的范围内）、交付物可机器检验（验收可以是一段脚本）、错误可逆（没有人类把关就不产生不可逆的法律或物理后果）、重知识而轻关系。微 SaaS、数字内容运营、数据服务与自动化增长运营都满足这些标准。

注意这个框架对自动化之辩意味着什么：OPC 不会摧毁行业。它释放供给——一些此前对一个人来说过于沉重的业务形态由此变得可行。市场会得到更多、更小、更锋利的公司。

### 公司是分形

这套设计的最后一个特性是自相似（**图 3**）。整个公司是一位创始人加若干部门经理 AI；每个部门是一个经理 AI 加若干工人 AI；每个项目是一个规划 AI 加若干执行 AI。三个层级，同一种模式：一个编排者，若干受协议约束的执行者。

<figure class="figure">
<img src="/assets/images/fig3-fractal-company.svg" alt="一人公司的自相似结构" loading="lazy">
<figcaption class="figcaption"><b>图 3 | 公司是分形。</b> 公司、部门与项目三个层级共享同一种模式——一个编排者加上若干受协议约束的执行者——因此，一个经过验证的工作室无需重新设计就能复制成各个部门，而创始人的角色每复制一次就上升一级。</figcaption>
</figure>

一个运转顺畅的工作室，要变成公司并不需要重新设计；它需要的是复制。工作单 schema、汇报模板与验收脚本——在三人工作室里验证过一次——被复制进财务部、内容部、运营部，只需替换知识层与技能集。创始人的角色随每次复制而上升：起初是唯一的执行者兼编排者，然后只做编排，最后成为任命编排者、批准预算的那个人。OPC 不是靠招人成长，而是靠复制一套已验证的模式。

## 讨论

**与既有工作的关系。**ChatDev<sup>2</sup> 与 MetaGPT<sup>3</sup> 展示了单一项目内的角色扮演；本设计把协作延伸到组织层面——持久角色、跨项目记忆，以及比任何单一任务都活得更久的治理。AutoGen<sup>5</sup> 提供灵活的对话拓扑，CrewAI<sup>9</sup> 这类基于角色的框架则补充了编排原语；两者提供的都只是*机制*，而本文提出的工作单 schema 提供的是*语义*——带明确定义状态的义务、验收与证据。Anthropic 关于“高效的智能体偏好简单、可组合的模式”的指引<sup>6</sup>，与我们的做法一致：用文件、约定和一个受版本控制的收件箱，而不是一个铁板一块的运行时。

**局限性。**本文是设计立场论文，不是实证研究；各项机制已经分别得到验证——验收测试、上下文隔离、跨模型验证——但组装起来的完整系统尚未经过纵向测量。“跨厂商验证能使错误去相关”这一论断是一种启发式判断：模型家族共享训练数据的谱系，跨厂商之后盲区仍可能保持相关。token 成本核算在各厂商之间没有标准的比较单位，因此“薪酬”数字只能算作参考，谈不上可审计。

**未来工作。**有三个方向。第一，工作单协议的开源参考实现——一个基于 git 的最小收件箱，配一个 schema 校验器——可以让实践者在厂商标准化之前先收敛出一套共同约定。第二，*blocked_on_human* 状态值得做一项用户研究：不懂技术的创始人能以多低的成本衔接线下步骤、又不丢掉心流状态？第三，治理：随着 govern 类工作单不断积累，决策记录会汇成一个语料库，用来研究人类的把关在哪些环节确实必不可少、哪些环节只是仪式性的。

## 方法

本设计研究经由三条途径完成：（i）对基于 LLM 的多智能体系统与组织经济学的文献综述；（ii）在支持持久角色、调度器与委派原语的通用智能体平台上，对 AI 员工工作流进行迭代原型验证，结构化的工作单通过一个受版本控制的仓库交换；（iii）从软件工程（协议、最小权限）与组织理论（交易成本、例外管理）出发的类比推理。原型验证期间观察到的失败模式——角色之间的上下文污染、凭文字叙述而非证据来判断验收、无视预算的执行——正是“结果”一节各项机制的由来。图为手工绘制的矢量图形；引用合成未使用任何生成模型，全部参考文献均对照原始出处逐一核实。
