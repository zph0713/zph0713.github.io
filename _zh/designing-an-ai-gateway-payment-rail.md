每一个上线过 LLM 功能的产品团队，最终都会手写同样的五样东西：存放 API 密钥的地方、重试策略、限流器、用量计数器，以及一张记录这一切花了多少钱的月度表格。然后公司里的第二个团队又把它们重写一遍，而且写得还略差一些。这是一个模型充裕（model abundance）的时代——OpenAI、Anthropic、Gemini、DeepSeek、自托管的 vLLM——可每一次集成仍然像一份依赖一样被硬绑在某一家模型提供商身上，而不是成为一层基础设施。

一旦你把 AI 能力当作银行对待支付那样来处理，图景就完全不同了。一次对大模型的调用就是一笔交易：它有*付款方*（花谁的预算）、有*金额*（输入 token、输出 token）、有*交易对手*（哪家提供商、哪把密钥），还有一张*凭证*（一行审计记录）。从这个角度看，缺失的那块基础设施是一个 **AI 网关（AI gateway）**——不是 API 代理，而是一条支付轨道：逐密钥的路由、计量与控制。

这篇文章记录的正是这套系统的设计——我们一直以代号 *airoute* 在推进它。它是一份随笔形式的设计文档：问题是什么、架构长什么样、哪一项工程决策最费思量，以及一个概念验证（proof of concept，PoC）的实测数据——这些数据在生产代码一行未写之前，就改写了我们至少一个假设。

## 1. 这一通调用花的是谁的钱？

网关的核心，是每次请求都要回答的一个问题：**这通调用由哪把密钥买单？**与它相比，其他一切——吞吐、延迟、不同提供商之间的协议翻译——都算已经解决的问题；因为答案牵扯钱、权益与信任，而且必须在毫秒级内作出。

密钥的供给有五种模式，网关必须同时容纳全部五种，因为真实组织总是混着用：

- **BYOK**——终端用户自带上游密钥（比如：API 转售商的客户，或签有自家企业合同的内部团队）。
- **平台自营池（platform-operated pool）**——由网关运营方采购、在内部计量的密钥。
- **授权入池（authorized bring-in）**——用户按照"用量与收益分成"协议把自己的密钥贡献给共享池：每把密钥都可追溯，且一旦滥用就有权被清退。
- **合作伙伴池（partner pool）**——合作伙伴的密钥，按约定好的固定 token 单价结算；用量 × 单价按月结算，每一笔都有审计记录支撑。
- **自托管（self-hosted）**——本地与 OpenAI 兼容的端点（vLLM、LM Studio），网关把它们的地位等同于又一家提供商。

而在各个业务系统一侧，这一切都不可见。业务系统手里只有网关签发的一把**虚拟密钥（virtual key）**（`sk-air-*`）：它绑定一个租户（tenant），自带有效期、速率限制、模型白名单与预算。真正的上游密钥在静态存储时采用信封加密（envelope encryption），永不进入日志，也永不离开网关进程。一个业务系统无论是从 BYOK 切到平台自营池，还是从 OpenAI 换成本地模型，代码都不用改一行——路由层会把这一切差异吸收掉。

路由本身是两个叠加的决策。**第一层是来源决策：这通调用花的是谁的钱。**调用方用户若持有一把健康的 BYOK 密钥，流量就路由到用户自己的密钥上；否则调用沿一条可配置的优先级链逐级下探，落入平台自营池。这条链是策略而非代码，所以一个租户不需要发版就能重排它的顺序。**第二层是池内选择：**给定一个池子，这次请求具体由哪把密钥承担？每个池各自声明自己的策略：

**表 1.** 池内密钥选择算法。

| 算法 | 思路 | 最适合 |
|---|---|---|
| round-robin | 轮流使用 | 同质密钥组成的池 |
| least-busy | 选在处理中请求最少的一把 | 自托管、对容量敏感的场景 |
| quota-aware | 按剩余 RPM/TPM 加权 | 上游限额不一的密钥 |
| cost-first | 优先选单价最低者 | 平台自营池、成本控制 |
| latency-based | 按历史 p50/p95 加权 | 对延迟敏感的租户 |

策略之下，还运行着一套按密钥维度的健康体系：连续 429/5xx 计数会把一把密钥送入冷却，随后自动移出；恢复之后，再重新启用。一次失败的调用会沿梯子逐级下探：在下一把密钥上重试，再沿模型降级链（fallback chain）往下走，最后才如实报错——每一级都会在账本（ledger）里留下标记（`degraded: true`）。有一条边界是刻意为之：BYOK 密钥失败时*不会*静默回落到平台自营池——因为那等于未经同意就花别人的钱。这是需要显式开启（opt-in）的策略，永远不会成为默认行为。

整条决策链，压缩成一张图：

![一次调用的完整路径，由六道可配置的闸门组成：层级闸门、缓存查询、来源决策、密钥选择、配额闸门，然后是调用与计量——另有三个带计量的出口：缓存命中、超出配额、上游失败](/assets/images/fig-airoute-call-route.svg)

上面每一道闸门读的都是实时状态——套餐、路由规则、池策略、密钥健康度——所以整条路径是纯粹的策略。这正是设计目标：**请求路径保持无聊、保持快速；一切有趣的业务规则都活在数据里。**

## 2. 一张图看懂整个系统

承载这套路由的架构，外表刻意保持常规——FastAPI + asyncio，无状态网关节点，底层是 Redis 与 PostgreSQL——内里却只有一处不寻常：引擎边界。下面这张图画的就是整个系统，重点是各方各拥有什么：

![airoute 网关架构：业务系统用虚拟密钥调用一个与 OpenAI 兼容的端点；在自建范围内部，数据面（入口、路由器、调度器、计量）与控制面（租户、密钥池、计费、策略、webhook、对账）与进程内的 litellm 引擎及共享的 Redis/PostgreSQL 存储并存；上游提供商——OpenAI、Anthropic、Gemini、DeepSeek、本地 AI——全部经由同一条路径接入](/assets/images/fig-airoute-architecture.svg)

这张图里藏着三项值得明说的结构性决策。

**控制面与数据面是分离的。**请求路径只做五件事——认证、决策、调度、翻译、计量——除此之外什么都不做。所有业务规则（谁能用哪个层级、超额（overage）怎么办、池子如何结算）都活在请求路径旁边的控制面里，可以自由演进而不触碰路径本身。正是这一点，让网关能够用一个代码库同时服务多个采用不同套餐与策略的业务系统。

**无状态节点，有状态存储。**速率计数器、语义缓存（semantic cache）与计量队列放在 Redis；元数据、计费账本与审计放在 PostgreSQL。网关节点自己不持有任何状态，因此扩容就是加副本——从一台 docker-compose 主机扩到一个小型集群，都不用重写。

**引擎是一只带硬边界（hard border）的盒子。**开源翻译引擎 litellm 以*进程内*方式运行——但它是一份带契约的依赖，而不是我们要去扩展的平台。下一节就讲这条边界，因为它是整个设计里代价最高的一项决策。

## 3. 引擎止步之处，正是我们开始的地方

构建 AI 网关的标准做法是 fork 一个代理——LiteLLM Proxy 及其同类产品出厂就自带路由、预算与密钥。于是标准的本能反应就是：把代理拿来，改一改，上线。我们否决了这条路，而其中的理由正是整个设计的核心。

代理是一个带着自己立场的单体。LiteLLM Proxy 把认证、团队管理、预算与路由耦合在同一个代码库里；本网关需要的功能——逐请求的 BYOK 路由、带收益分成的授权密钥池、带超额策略的订阅计费——全都*不在*它的模型里。把它们塞进去，意味着要对一份每周都要与上游 rebase 的代码库做大手术。每一次升级都变成一场合并冲突抽奖；你最终会停止升级，然后永远拥有一份 fork。

另一个极端，是所有 provider 适配器都自己写。那是十年积累下来的工作量——100 多种 provider 的协议怪癖、流式语义、重试行为、成本表。为了省去集成的麻烦而重写这一切，正是工程师们烧掉一个又一个季度的方式。

中间路线，也是我们的选择：**网关自己写，litellm 只作为引擎库使用，绝不当代理用。**网关在进程内调用 `acompletion`，并*逐请求*传入 `api_key`、`api_base` 与 `model`。正是这一项能力——由网关、而不是代理配置来决定每个请求携带哪把密钥——让 BYOK 路由与池级调度完全归我们掌控。litellm 继续干它无人能及的那份活：把一次请求翻译成 100 多种 provider 的方言，流式也包括在内。

**表 2.** 让一个快速演进的依赖不至于变成负债。

| 层面 | 策略 |
|---|---|
| 依赖管理 | 锁定版本（litellm==x.y.z）；升级一律以带契约测试的 PR 进行 |
| 隔离 | 所有引擎调用都经过统一的 `adapters/` 层；业务代码从不 import litellm |
| 契约测试 | 完整的 mock provider 测试套件——流式、错误、速率限制、用量字段——每次升级都全量跑一遍 |
| 回馈上游 | 通用功能以 PR 形式回馈上游，让下一次升级自动白拿这些功能 |
| 兜底方案 | 上游拒绝关键功能时：fork 那个*库*（改动面小），或做 vendor 化——绝不 fork 代理 |
| 旁路 | 完整版代理依然存在，供内部轻量场景使用，刻意排除在商业计费之外 |

这条边界规则值得用一句话说清：**引擎永远看不到用户身份或计费逻辑——它只看到一把被选好的密钥和一份待翻译的请求。**litellm 在钱的逻辑上缺的任何能力（路由决策、计量、策略），都是我们架构使然、天生自带，而不是靠补丁打上去的。万一将来出现更好的引擎，我们只换一层，不动整个系统。

## 4. 计量要像银行账本，而不是像日志文件

如果说路由是网关的大脑，计量就是它的神经系统——而且它与银行账本共享同一条不容妥协的性质：必须完整、可归因、绝不可能丢失。每一次调用，缓存命中也不例外，都会产生一行原子记录：租户、用户、虚拟密钥、池、上游密钥、模型、输入 token、输出 token、成本、延迟、状态、是否命中缓存或降级。`request_id` 让这一行具备幂等性——重试不会造成重复计数；一旦你的客户端会重试，这一点的重要性远超听上去的样子。

有两个实现细节值得抄走。第一，token 计数取自模型自己的 `usage` 响应——网关从不自己数 token——流式请求在**流尾（stream tail）**捕获用量，因此响应绝不会为了记账而被缓冲。上游没有返回 usage 时，网关注入一个估算值，并把该行标记为 `usage_source: estimated`——诚实的估算，好过账本上一个无声的窟窿。第二，请求路径绝不为存储而阻塞：用量行写入 Redis Stream，由 worker 批量插入按月分区的 PostgreSQL。网关用几秒钟的记账延迟，换来请求延迟的零增加——而计费系统需要的不是实时，是*完整*。

账本之上，是各种结算模式：面向用户的订阅（月度 token/请求配额、允许使用的层级、一套超额策略——可以拦截、可以提示升级、也可以降级到更便宜的层级）、面向 BYOK 用户的用量账单、合作伙伴池的月度结算单，以及授权入池密钥的收益分成账单（分成所得可抵扣贡献者自己的订阅费）。缓存命中与影子模式（shadow mode）的调用按各自的特价计费。这一切都不触碰请求路径；它们读的都是同一份账本。

## 5. 让池化密钥比单把密钥更省钱的几个杠杆

网关一旦开始*省* token 而不只是*整理* token，它存在的理由就翻倍了。五项增值能力从第一天起就设计在内，而不是日后外挂：

**表 3.** 增值层：全部由策略驱动，全部被计量。

| 杠杆 | 作用 | 备注 |
|---|---|---|
| 语义缓存 | 非流式、可缓存的调用命中租户隔离的缓存 | 估算：重复性负载可节省 70–90% 的 token |
| 降级链 | 按模型别名配置：主 → 备 1 → 备 2，遇 5xx/429/超时触发 | 响应标记 `degraded`，可选通过 header 向外部透出 |
| 任务分层路由 | 业务方通过 `X-Task-Type` 或别名声明任务类别（`summary-fast` 对比 `summary-ultra`） | 由套餐决定哪些层级可触达 |
| 用量 webhook | 在 80%/100% 阈值与异常时触发的签名、重试、幂等回调 | 让业务系统自行卡住自家的付费墙 |
| 金丝雀与影子（canary & shadow） | 新模型加权金丝雀发布，一条命令即可回滚；影子模式对比响应但不计费 | 影子流量记在独立的成本代码之下 |

缓存是那匹出人意料的黑马。一个作业讲解类服务——网关运营方的第一个租户最爱跑的那类重复性高、相似度高的负载——大部分流量都可以直接命中缓存，用户能察觉到的只有账单在变小。V1 上线精确匹配缓存（请求哈希）；语义相似（embedding + 阈值，余弦 ≥ 0.95）放到 V2。隐私规则很严格：BYOK 调用与标记为敏感的任务永不缓存，租户之间相互隔离，TTL 可配置，任何请求都能强制绕过。设计把缓存当作一个计费产品，而不是性能把戏：命中按缓存价计量，账本能精确展示缓存到底省下了多少钱。

## 6. PoC 证明了什么——以及它发现的那道悬崖

在 M1 之前，我们先做了一个概念验证：一个真实的网关进程、一个会记录每个请求落在哪把密钥上的 mock 上游，外加一套测试。它花掉一个周末，却改写了风险清单。七项集成测试全部通过：逐请求的密钥注入确实把 BYOK 流量路由到用户自己的密钥（在 mock 侧验证）；带 429 故障转移的池内轮询正常工作并标记 `degraded`；BYOK 失败默认*不会*泄漏进公共池；流式用量在流尾捕获；缺失的 usage 获得估算注入处理；认证、别名映射与幂等计量都站得住。

性能测试更有意思。有两个数字并不意外：热网关处理一次串行调用约 2.7 ms；冷启动初始化在前几个请求上要花 236–500 ms（litellm 的客户端构造所致——因此 V1 强制加入启动预热）。第三个数字让我们大为意外。

![实测网关吞吐量随并发变化：100 个连接时爬升到 2276 QPS，越过约 120 后出现断崖——uvicorn 的 h11 延迟爆炸，250 个连接时只剩 417 QPS；而把每密钥信号量上限设为 100 后，吞吐稳定维持在 2021 QPS](/assets/images/fig-airoute-concurrency-cliff.svg)

直觉上，更多的并发连接应该带来更高的吞吐，直到 CPU 耗尽为止。然而 uvicorn 的 h11 协议服务器在约 120 个以上并发连接处陡然坠落：100 个连接跑出 2276 QPS，250 个连接只剩 417 QPS——是五倍的崩塌，不是平台期。客户端连接池的过度订阅让情况雪上加霜，请求在客户端库内部排起长队。这正是真实网关会最先撞上的失效模式——因为真实的业务系统不会一次只来一个请求。

解决方案其实早已在设计之中，但这次测量把它从"锦上添花"升格为"铁律"：**每个上游密钥一把并发信号量（semaphore）。**每把密钥一条带上限的队列；网关在上游看到任何 429 之前，就先约束住自己。信号量上限设为 100 后，一次 300 请求的突发以 2021 QPS 平稳跑完，p50 延迟 44 ms——平坦、可预期、没有断崖。这个教训可以推广：对任何挡在别人限速规则前面的组件来说，自我约束不是性能细节，而是正确性模型。

PoC 还逮到了三个值得记录的坑。litellm 底层的 OpenAI 客户端会自行重试（`max_retries=2`），叠加在我们的重试层之上，把一把失败密钥承受的压力放大了三倍——重试策略必须收敛到同一处。litellm 在 import 时会尝试从网络拉取模型成本表，在受限网络下会让启动卡住 30 多秒——一个本地成本表开关就能解决。另外，litellm 每个请求都会新建一个 `AsyncOpenAI` 客户端，所以连接复用必须显式地设计出来。这四项——连接复用、启动预热、重试收敛、按密钥信号量——就是 M1 的检查清单。

## 7. 从设计到生产

路线图分三个阶段推进。**M1** 交付主干：与 OpenAI 兼容的端点、虚拟密钥、自营池加 BYOK 路由、原子计量账本、基础订阅配额与管理 API——足以让第一个业务系统承载真实流量，并在账单里看到每一次调用。**M2** 加上增值层：语义缓存、降级链、任务分层路由、用量 webhook、本地 vLLM 与管理界面。**M3** 走向商业化：授权入池、合作伙伴结算、对账报表、金丝雀与影子模式，以及高可用部署。PoC 已经干掉了最大的架构风险；剩下的主要只是范围与纪律的问题。

**表 4.** 里程碑。

这一切都不稀奇。网关的组成部分不过是一个无状态 API 服务、两个存储，外加一个借来的翻译引擎。设计过程反复揭示的是：真正的难题全是**边界问题**——这一通调用花谁的钱、哪些逻辑可以放进第三方引擎、缓存允许出现在哪里、什么绝不允许被悄悄计量掉。正是这些边界，把一堆密钥变成一条支付轨道——而这恰恰是任何代理厂商都不会卖给你的部分，因为那是你的商业模式，不是他们的。
